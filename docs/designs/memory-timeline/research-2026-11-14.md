# Voice and gesture memory timeline: feasibility research

Date: 2026-11-14. Status: research intake for EGM brainstorming, not an approved design or completed Goldfish review.

## Assessment

A Mac application that searches saved conversations and selected photos by voice, then browses the results with Vexo wrist gestures, is technically plausible. The largest unknown is reliable intentional gesture recognition during ordinary activity. A useful demonstration is achievable with a small, deliberately assembled collection; dependable all-day autobiographical recall is a substantially larger project.

This is a targeted survey of primary Apple documentation, wearable interaction research and episodic-memory research, plus inspection of the current implementation. It is not an exhaustive search of the internet or evidence that the proposed application outperforms other products.

## What recent research changes

**Finger gestures need the appropriate sensors.** Meta's 2025 neuromotor interface uses surface electromyography, including 16 bipolar recording channels. Its finger gestures and handwriting results cannot be transferred to an accelerometer/gyroscope band by adopting the same model. Vexo is a candidate for deliberate wrist swipes and rotation, but reliable finger pinch detection is unsupported by the present evidence. [Nature paper](https://www.nature.com/articles/s41586-025-09255-w).

**Memory answers must include evidence.** The 2026 S-EMBER preprint evaluates streaming wearable memory with both answers and precise supporting video intervals. Its results expose a gap between answering plausibly and locating the evidence. Our photo/transcript collection differs from its video benchmark; the relevant design lesson is to evaluate the returned source and time as well as the answer. [S-EMBER](https://arxiv.org/abs/2607.02689).

**Local photo retrieval has practical model candidates.** Apple's MobileCLIP2 research provides image/text representations suitable for semantic image search. It merits comparison with text-and-time search on the actual collection. Published model benchmarks are not latency measurements for this Mac or proof of personal-memory retrieval quality. [Apple research](https://machinelearning.apple.com/research/mobileclip2), [official implementation](https://github.com/apple-aiml-research/ml-mobileclip).

**Image description is a separate task.** Apple's FastVLM research addresses efficient visual question answering. It is an alternative candidate for describing a selected photo rather than a requirement to run a large model over every photo. Deployment, model terms and resource use need checking before selection. [Apple FastVLM research](https://machinelearning.apple.com/research/fast-vision-language-models).

| Need | Available route | Design implication |

| Timeline interface | Native macOS SwiftUI application | Semantic navigation within our own app avoids needing system-wide mouse control |

| Native transcription candidate | SpeechAnalyzer / SpeechTranscriber | Check hardware, locale, downloaded assets and audio format; benchmark separately |

The installed SDK and command-line Swift tools were observed earlier in this research, but no native application was built. Foundation Models runtime availability, Photos permissions and location permissions were not queried. The current caption backend uses Deepgram; adding local retrieval or summaries would not make that existing audio path fully local. Native Apple transcription is a later comparison, not a reason to replace the working backend before the timeline demo.

Vexo has no camera or GPS. Photos must come from imports, a photo library or a phone companion. Mac location describes the Mac's measured position, not a detached wearer. Recording a day away from the Mac requires a separate mobile capture/transport design; reliable background operation and reconnect behavior cannot be assumed.

## Working design hypothesis for discussion

Keep the existing caption service as the recording backbone. Add a separate memory reader and native timeline. A query such as “Show the photo around the conversation about the prototype” returns candidate moments with their original photo, transcript excerpt, time and uncertainty. The user can browse those results by wrist movement, select one and ask a follow-up.

The following are proposals for EGM to challenge, not decisions already approved by the user:

1. **Build a derived local index.** Read authoritative final events into a rebuildable index with stable event IDs. Store photo references and metadata separately. Handle replay, rotation, duplicate events and deletion explicitly. Do not edit transcript text to make it fit a generated story.
2. **Combine exact and semantic search.** Use time/source filters and lexical search for exact names or phrases, then semantic retrieval for paraphrases and visual concepts. SQLite FTS5 offers phrase search, ranking and snippets; it provides a useful baseline before adding embeddings. [SQLite FTS5](https://www.sqlite.org/fts5.html).
3. **Return sources before generating explanations.** Answer from the retrieved evidence, preserve links to originals and allow “not recorded.” A nearby photo and conversation are a suggested temporal association, not proof they describe the same event.
4. **Separate capture time from import time.** Retain timezone, clock origin and uncertainty where available. Avoid precise-looking cross-device alignment when clocks or photo metadata are uncertain.
5. **Reuse the existing Bluetooth owner.** A second app should not compete for the band's BLE connection. A future adapter in the existing owner can publish bounded semantic commands to the timeline, separate from the audio queue. Image indexing and model work belong outside the audio callback.
6. **Treat speech as data until control is explicitly activated.** Ambient conversation, television and stored transcript text must not become application commands automatically. Speaker verification remains uncertain and is not an authorization credential.

## Gesture interaction to test

Start with a visible, explicitly armed navigation mode. Candidate mappings are wrist swipe for previous/next moment, wrist rotation for timeline scale, and a deliberate tap for opening the selected card. These mappings can conflict: the movement that zooms may resemble the movement that scrolls. Test them before committing to all three.

Zoom must also have a clear meaning: changing the timeline's time range and enlarging a photo are different actions. A context indicator should make the active meaning visible. Selection should be reversible, with keyboard/trackpad equivalents for every action.

Use raw accelerometer and gyro samples at an initial 50–100 Hz, short analysis windows, calibration, a neutral position, hysteresis and cooldown. This is a starting hypothesis, not an accuracy claim. A simple detector is the baseline; collect consented labeled motion trials only if it fails. Do not send every sensor sample through an LLM.

The SDK supports these sample rates and higher ones, but higher rates consume transport and power budgets without proving better interaction. Existing built-in slow tilt behavior is not evidence of responsive zoom. See the [SDK API](/Users/alhinai/vexo-captions/vendor/vexo-open-kit/docs/api.md) and [Bluetooth contract](/Users/alhinai/vexo-captions/vendor/vexo-open-kit/docs/bluetooth-contract.md).

## What would make the concept fail

- **False activation:** normal talking, reaching and drinking navigate the timeline. Measure false actions during unprompted activity, not just accuracy during prompted swipes.
- **Weak retrieval:** the app returns a thematically similar conversation from the wrong day. Test duplicate topics, ambiguous dates, exact names and questions with no recorded answer.
- **Misleading identity:** speech captured by the wearer's band is labeled as theirs. Preserve uncertain speaker labels and connection-scoped diarization identities.
- **Gesture fatigue:** navigating is slower or more tiring than a trackpad. Compare task completion with voice-only and ordinary input; keep gestures only where they help.
- **False completeness:** the timeline looks like a complete day despite disconnected capture, missing metadata or unsaved photos. Display coverage gaps.
- **Unbounded processing:** image indexing or generation delays captions. Use bounded background work and compare existing audio health metrics before and during future tests.
- **Incomplete deletion:** removing a moment leaves searchable embeddings or generated summaries. Delete derived representations and prevent their reappearance on reindex.

## Evaluation before calling it successful

Use a small consented or synthetic collection with known answers. Include photos, conversation excerpts, repeated topics, missing location and unanswerable questions. No private audio is needed to prepare this fixture.

Agree on numerical targets before testing: correct source in the first few results, citation correctness, time alignment, appropriate unknown answers, command-to-screen latency, gesture success, accidental actions per minute and task completion time. Measure each gesture independently and compare combined interaction against voice-only and trackpad use. A polished scripted run alone does not establish reliability.

First validate the memory browser with conventional controls; then test discrete band navigation; then evaluate zoom and selection together. Phone collection, all-day operation, broad photo-library indexing and global desktop control should each justify their added scope separately. These staging recommendations remain open to review.
